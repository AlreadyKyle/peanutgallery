# Mob Machine: the constitution

This file says what the studio is and the rules it runs by. It holds no schedule: work is ordered, never dated, and no date or deadline appears here unless the board set it (18 September 2026). `docs/ROADMAP.md` is the launch checklist. `docs/BACKLOG.md` lists every mechanic that is planned and not built; the board files those entries as cards, and the site lists them on /roadmap. A spec under `docs/specs/` is the contract for one change. A mechanic that is not built gets one line here, in §4 Not built yet, pointing at its backlog entry, and is not described as if it exists.

Rewritten 22 September 2026 from the kick-off plan (version 3.4, at commit ed29674), which it replaces. The section numbers, the Kernel and The Board headings and the numbered decisions in §10 are kept, so a citation such as "PLAN.md §4 The Board" or "§10 default 20" in a spec, a migration or a code comment lands on the same subject; specs and migrations dated before 22 September 2026 quote the kick-off plan's wording. The working name Backseat survives in the package names (`@backseat/*`).

## 1. Decision

The studio goes live when every criterion in `docs/ROADMAP.md` holds and the board presses Go live at /board. There is no launch date. Everything outside that checklist is in `docs/BACKLOG.md` and reaches the studio as cards after Go live, built through the studio's own system (§10 decision 24).

## 2. Concept

A public game studio run by AI agents, directed by its audience and funded by the hour. Agents build free, browser-playable games. Supporters fund the cards they want built: a card is one small change with a funding bar, and when its bar is full the agents build it, automated checks test it, and it goes live. The studio spends only what has been funded, shows the cost of all agent work paid for with contributions on a public ledger, and lets each supporter set at checkout how much of their contribution runs agents and how much pays the studio. Work billed to the founder before the cutover is tracked privately (§4 The Board, §10 default 7). Star Citizen has raised over $1B in 14 years without a 1.0 release; here every dollar is visible as work.

A continuous stream of the studio at work, with a host, is part of the concept and is planned, not built: the launch is site-first (§10 default 15), and the stream is in §4 Not built yet.

Prior art. Multiverse Studios runs AI agents as a dev team on MIT-licensed games with a live view of the agents; it has no voting, no funding-throttled throughput, no seasons, and no show. Neuro-sama was the most-subscribed active channel on Twitch in January 2026. Twitch Plays Pokémon drew 1.16 million participants in 2014. Polsia runs whole companies on agents that work while the owner sleeps and re-engage the owner with a daily report. This plan combines the four and adds the funding meter.

Pitch line: "Watch AI agents build a game studio and free games. Fund the card you want built next." (22 September 2026: funding a card is the choice, §10 decision 21; 27 September 2026: the pitch names no game, §10 decision 58.)

## 3. Scope and the team

One seed: Dust, an idle/incremental game in `seed-1/`. In that genre a proposal is a number, a rule, or a new unit, which is the cheapest thing to change in minutes. The studio is named Mob Machine (§10 decision 43).

Sixteen roles, each a role spec in `platform/agents/` (JSON plus a prompt) that names its place in the launch roster: running at launch, starting on a named trigger, or planned (`platform/agents/README.md`). Running at launch: Studio Head (the roadmap, the numbers and the org chart; it proposes and does not decide), Game Designer (designs each game card for the Game Director to grade), Game Director (the pillars), Builder A and Builder B (Game and QA cards in `seed-1/`), QA (bug reproductions and fixes), Platform Builder (studio cards in `platform/site/`), Platform Director (the site's standards; it grades studio cards) and Janitor (drift checks, as code only; its docs pass comes later). Starting on a named trigger: Head of Finance (explains the money, from the cutover), Tech Artist (the game's look, as code), HR (the role specs), Head of Product (product reviews), Biz Dev (tools and trends from outside the studio; the Scout until 23 September 2026) and Community (the studio's own community). Planned: Host (the stream's narrator). The Host, Biz Dev and the Community agent read outside text and have no write tools.

Each role has a trust class that sets what it may do (`docs/SYSTEM.md`): writers change the paths their card names (Builder A, Builder B, QA, the Platform Builder and the Tech Artist); planners draft and rank cards as structured output (the Studio Head, the Game Designer and HR); reviewers grade and approve (the Game Director and the Platform Director); read-only roles read the repository and the books (the Janitor and the Head of Finance); web-only roles read outside text and write nothing (Biz Dev, the Head of Product, Community and the Host). A role has write access exactly when it is a writer or a planner with tools. The Studio Head and the two Directors hold Read, Glob and Grep: they read the repository and change nothing in it. The Game Designer holds them and Bash for seed-1's package scripts, in a scratch checkout of main the dispatcher throws away: it writes card drafts, never files.

What runs at launch. Four roles run cards: Builder A, Builder B, QA and the Platform Builder, and the Platform Builder has no card until the studio code lane opens, which the board does once its own site is live (§4 Work). Two role jobs run when the board starts them at /board: Rank now, where the Studio Head orders the open cards on now, and Draft a game card, where the Game Designer drafts a new seed-1 card and the Game Director grades it in a separate session (§4 Who files cards). Both run attended on the founder's plan while a board member is signed in, in either studio mode, billed to the founder, so no role job spends studio or supporter money (`docs/specs/agent-workflows.md`). Note triage, the Monday report and the Studio Head's own drafting are backlog. The seven roles added on 23 September 2026 have role specs with no tools and no job that runs them yet, and the Host, Biz Dev and the Community agent are not running yet. The /team page shows which roles build cards from those facts, and says that some of the others rank, draft or grade cards when the board asks.

The team, on screen. Every agent is an alien: a small, strange, friendly creature, one plain line in its role spec's `species_note`. The avatars are drawn in code as SVG from one style (§10 decision 27). The /team page shows each role's name, title, "AI agent", what it does, whether it can change the game or the site, its model, its hire date, live cards shipped and studio spend. Every card carries "AI agent" in plain text. Names equal titles until the roster is named through the name pipeline. Rituals map to real events only: no daily standups, no scripted conflict, no vacations, no equity, no backstories, no claimed experience.

## 4. Mechanics and kernel

### Cards

A card is one unit of work. It carries a title, a public summary (one line), the agents' brief (the intent), a deterministic acceptance test with `check:` lines, a lane, a folder, an executor role, an estimate in dollars, a funding target, a bucket, a source (board, community, agent), a shape, a stage, a horizon and a rank. The acceptance test's machine line is `check: config <file> <path> == <json>`; the dispatcher evaluates it false on `main` before the session and true after it, and the smoke test reads the same value from the served file.

Stages: proposed → designing → voted → funded → building → gated → live, or rejected with the failing check attached, or paused. `voted` is the stage name for a card open for funding; nobody votes at launch. A session stops when its cost reaches the card's ceiling, the lower of 150% of the estimate and the per-card maximum; the card then pauses for the board, which may resume it with a new estimate no lower than its actual (`resume_card`) or cancel it with a reason (`cancel_card`). A cancel works only on a card that is proposed, designing, open, funded or paused, never on one that is building, gated or live; money on a cancelled card funds later cards. Actual cost is written back to the card.

Horizons: now, next and later. Only a card on now can take money or run. Next and later are the backlog: planned, not built, not open for funding, and listed on /roadmap. The board moves cards between horizons and sets their rank (`set_card_horizon`, second factor, reason recorded). A card that holds money cannot leave now.

Approvals. A card an agent wrote any of (source agent, or a drafter set) needs an approval before anyone outside the board sees it, it runs or it takes money: a row of the append-only `card_approvals` whose content hash (bucket, lane, folder, executor, title, summary, intent, acceptance test, design spec URL and funding target; not the estimate) is the card's current one. The dispatcher records an approval from the grader's own result through `record_card_approval`, which enforces separation of duties in Postgres: the approver is never the card's proposer, drafter or executor, a card's check-line author is never its executor, a grader's session is never the maker's, and only a reviewer or planner approves (a writer only for QA's verification). On a card that needs an approval a hashed field changes only through a board control, and the board's edit records a board approval of the new content. Board-filed cards need none.

Dealing and the cooling window. An approved agent card waits at proposed on next or later until `opens_at`, its approval time plus the cooling window, which the board sets from 0 to 10,080 minutes and which ships at 0. The first dispatcher tick after that deals it to now if it is still approved, vetoed by neither the board nor the Director, its executor role is not paused and it meets the definition of ready. Every funding path requires now, so no money reaches it before then.

Vetoes and role pauses. The board vetoes or unvetoes a card with a reason at the second factor; a vetoed card is never dealt or run, one on now with no money moves to next, and a card holding money is cancelled instead. The Director's stance is a separate field. The board or the moderator pauses a role, and only the board resumes it: a paused role starts nothing, and its running card session stops at the next watch with the card back at funded.

Resume by rule. A card paused at its ceiling for the first time resumes with no one acting when the money on its bar covers the room a new ceiling adds: its new estimate is its actual cost, its new ceiling the lower of 1.5 times that and the card maximum, and a short bar is topped up from Not on a card yet, all or nothing, never from another card. A card at the card maximum, or paused at its ceiling a second time, waits for the board (`docs/specs/agent-system-core.md`).

### Definition of ready

A card may move to now only with a title, a summary, an intent, an acceptance test with `check:` lines, a lane, a folder, an executor and a funding target. The executor must be an active role. `set_card_horizon` refuses a card that falls short (22 September 2026).

### Who files cards

The board files cards at /board or through reviewed scripts, and supporters choose among the open cards by funding them. Game cards can also be drafted by agents, when the board presses Draft a game card at /board: the Game Designer drafts one new seed-1 card (title, summary, intent, `check:` lines, lane, executor and one estimate, which is also its funding target); the dispatcher refuses it, naming the check, if it fails its schema or the definition of ready, has a `check:` line that does not parse or already holds on main, touches a kernel path or a folder other than seed-1, carries a deny-listed term, estimates above the per-card maximum or names no active, unpaused writer; and the Game Director grades a draft that passes, in a separate session, against the pillars and the rating (`platform/agents/rubrics/draft-game.md`). Approved inserts the card on next with its approval, and the tick deals it to now after the cooling window; revise starts another Designer round, at most three; flagged, or a third round without approval, withdraws the draft and writes no card. Drafts are private until approved. When the board presses Rank now, the Studio Head orders the open cards on now that step 2 funds and that hold no money on their bar or on hold, and the dispatcher writes rank only: the named cards trade the ranks they already hold, so every other card, one holding money included, keeps its place in the waterfall's line; at most ten changes a run, with one event, which the public reads as the Studio Head ranking the cards open for funding (the moved cards and their ranks stay on the board's run output, and the public sees the new order on the cards). Both roles see typed card fields only: a card a supporter or the community proposed reaches them as its id, stage, horizon, bucket and funded amount. Every agent-written string a stranger can read passes the gate's own deny-list scan before it is written. The site shows "Written by the <role>, an AI agent" beside agent-written card text. The founding intent stands: the board steps back from routine Game cards once agents and the audience propose them, through the Studio Head's own drafting and free voting (§4 Not built yet).

### Funding a card

A card open for funding has a target and a bar. A payment's credit is the agents' net amount (after Stripe's fee, the 10% reserve, the supporter's studio share and the incident carve-out, less any hold), and one waterfall places every piece of it (`docs/specs/money-logic.md`, §10 decision 41):
1. the card the payment named, up to its target, if that card takes money;
2. the cards that take money in the Studio Head's rank order (unranked last, then oldest), each up to its target;
3. whatever is left, to Not on a card yet.

One predicate decides which cards take money at every step: a goal card on now with room under a target above zero, proposed, designing, voted, or funded but below its target, that the dispatcher could start once funded (vetoed by neither the Director nor the board, a board, agent or decision card, with a current approval when an agent wrote it, with an executor, and not in the closed platform code lane). A full bar means the pool holds the card's cost, and a proposed or voted card moves to funded. Released holds, a won dispute's reinstatement and a card's leftovers enter the same waterfall; every five minutes a sweep moves a shipped or rejected card's unspent money on and drains Not on a card yet onto the cards that take money. Contribute opens a chooser with "Fund the next card in line" first. A card's funding target is not bounded by the per-card maximum, which limits only what agents may spend on one card (§10 decision 28).

### Work

What a card may change depends on what kind of work it is (22 September 2026).

- **Game work** ("Dust", folder `seed-1`): changes to the game.
- **Studio work** ("The studio", folder `platform`): changes to the public site's pages, copy and presentation that the Platform Builder can make in `platform/site/` outside the kernel paths. The site's money, ledger and legal surfaces are kernel paths: the Payment Link and what reads, formats, states or shows money, the snapshot every figure comes through, the Contribute and Ledger pages and the legal pages, and the entry, top bar, footer and routes that frame them (§10 decision 39). The files that set the look are board work too, though not kernel (`platform/gate/design-paths.txt`: the tokens, the Card, the glyphs, motion, the route list `routes.tsx`, the site's public and brand files and the game's favicon), so a new page or screen is a board pull request (§10 decision 51). The board has its own site, so no card-built code ships beside the board's sign-in. The studio code lane opens when the board sets `studio_state.platform_lane_open`, once that site is live and the public site holds no session; until then the dispatcher refuses a platform code-lane card, and `file_card`, `set_card_horizon` and `resume_card` refuse to put one on now. The studio category is hidden on the site while it has no cards.
- **Board work**: how the studio runs, meaning the rules, the money, the card system, the dispatcher, the gate, the agents and their prompts, and the files that set the look. These are kernel or board-only changes, made only by the board through reviewed pull requests, never by a funded card. An agent may describe one as a proposal for the board.
- **The visual review**: a card whose change draws a page or the game differently gets frames from the gate (screenshots of the base and the change, the ones that differ kept as before and after pairs). After its gate passes, the Game Director (seed-1) or the Platform Director (the site) reviews them against `platform/agents/rubrics/visual.md` in one attended session while a board member is signed in, billed to the founder, and the card waits at gated until one is. All pass merges; a revise sends the builder the failing criteria, frame names and reason codes, at most twice; after that an all-ages revise rejects the card as a gate failure does, and any other open criterion ships with its verdict recorded. Sizes, spacing and counts are code's to measure: the site's design suite (accessibility, sideways scroll, reduced motion and layout balance) is kernel and runs in the gate (§10 decision 51).
- **Next game**: cards for the next seed. The category shows only once such cards exist. A new game is mobile-first from its very first version, prototypes included: its play screen fits a 375 by 812 portrait phone with no sideways scroll, every control is at least a 44px touch target there, and nothing needs a hover or a keyboard. Its harness, which the board writes with the new seed's folder, draws its frames at that size and measures those three in the gate, as seed-1's frames do (§10 decision 56).

Buckets (game, platform, qa, studio, budget, agents) stay an internal tag on each card; the public category comes from the folder.

### Lanes

Config-lane cards touch data, not code: tuning values, names, palettes, copy, unlock order, spawn tables (files under `seed-1/config/` and `seed-1/content/`). They run the scans, the headless bot and the build, and ship within minutes. Code-lane cards touch anything else outside the kernel paths and run the full gate. A card that needs a new function is code lane.

### Card shapes

At launch a card is either open for funding against a bar or a board directive. The schema also knows one-off and standing shapes; standing bars and the design stage for large cards are in §4 Not built yet.

### Incident reserve

5% of every contribution's Agents share goes to the incident reserve until it holds $500, with overflow returning to the pool; its balance is on the meter. A card marked S1 may draw on it in addition to the pool. Classifying severity by deterministic rules is in §4 Not built yet; until then the board sets a card's severity.

### Metrics

Each role spec names two or three scored metrics. First-pass gate rate: cards passing the gate on first run divided by cards attempted, trailing seven days. Cost per shipped card: ledger dollars divided by shipped cards, trailing seven days. Estimate accuracy: median of |actual − estimate| / estimate, trailing 20 cards. Bug reopen rate: QA cards reopened within seven days divided by QA cards shipped. Roles are data: a role spec holds purpose, prompt, tools, model, budget share, voice and its metrics. Publishing the metrics as scorecards is in §4 Not built yet.

### The weekly report, Discord posts and the card supply

- **The weekly report.** A report covers one New York week, Monday 00:00 to the next Monday 00:00. pg_cron calls `publish_weekly_report()` every hour; it publishes the last ended week once, and a week in which no card shipped gets no report. Its facts come from public records through SQL, never from an agent: each shipped card's title, folder, live time, cost from contributions and supporters by number, the number shipped, the cards open for funding and the first three in line, the new supporters and the week's spend from contributions. `/reports` lists them, newest first, through a fixed kernel template (§10 decision 50).
- **Discord, outbound only.** The dispatcher posts each card that ships (within 6 hours of going live) and each new weekly report to the studio's Discord webhooks, at most once each: it records the post in `outbound_posts` before sending, and a timeout, error or crash loses that post rather than doubling it. Nothing is posted while the studio is paused or the kill switch has fired, and a ship found then is never posted. With no webhook set, the lane makes no request. Discord is for ages 13 and over; the posts link back to the all-ages site.
- **The card supply floor.** `studio_state` holds a floor of open cards (6), of cards with a target of $5 or more (1) and of cards under $2 (1). /board shows the supply against it, and Needs you lists a shortfall with Draft to the floor, which queues the Game Designer's `draft_card` at the second factor, attended, like every role job. A board pull request changes the floor.

### Upkeep

- **The daily check.** The Janitor's `janitor` job, code only, runs each day, while the studio is paused too. It compares production's schema with the migrations object by object, each `MODEL_*` value with the price table, Anthropic's model list and the newest eval result, the installed Claude Code with its pin, and reads the weekly scan's result and three producer signals: a funded card unclaimed for 24 hours while the studio runs, a card paused at its ceiling within seven days, and fewer ships in seven days than half the seven before while funded cards wait. Each difference is one finding, listed in Needs you and sent once to ntfy, and closed when its check passes. Findings reach the board only: no agent reads them, and no finding changes code or files a card.
- **The weekly scan.** A read-only workflow on main runs osv-scanner over the lockfile and lychee, offline, over the docs, each action pinned by sha; the daily check lists each failed job.
- **Dependency updates.** Dependabot opens npm updates weekly once a release is seven days old, patches grouped, one pull request at a time, and GitHub Actions updates monthly; pnpm refuses a version younger than seven days and a downgrade in trust. The dispatcher's `upkeep_merge` merges a Dependabot patch only when every condition of the merge policy holds, at its exact head sha on a green gate, then deploys, smokes and rolls back as for a card; every other update waits for the board (§10 decision 53).
- **The Claude Code pin.** Attended sessions run only on the Claude Code version recorded with a passing `sandbox:check --positive` line; the adapter pauses a card with `cli_version` on any other, and the board's one `sudo` script turns the CLI's auto-updater off. A new version is a board pull request.
- **The replay eval set.** Frozen draft cases with expected outcomes, replayed attended on the founder's login with no API key and no database row, give pass^k per set. A change to a role prompt, rubric, agent definition or schema under `platform/agents/` merges only with a new result at or above the baseline, and a baseline moves only in a board pull request that gives the reason (§10 decision 52).

### Rating

The studio and everything it produces is all-ages. Games meet an ESRB E / PEGI 3 bar: no sexual content, nudity or suggestive themes; no realistic blood or gore; no drugs, alcohol or tobacco; no profanity or slurs in any string. The gate runs a deterministic deny-list (profanity, slurs, sexual and drug vocabulary, coded and leetspeak variants, maintained in `platform/gate/denylist/`) over every string, asset filename and commit message; a hit fails the gate with the term shown. Any generated image passes the provider's safety filter and a human review before first use. The Game Director's pillars include the rating. Rating labels appear on the site and in the game. Any incident that reaches the public triggers a post-mortem on the ledger page and a kernel patch before the affected feature resumes; once the stream exists, the kill switch comes first.

### Art policy

In-game art is procedural or vector, generated by code, never by an image model. The agent avatars are drawn by code too, as SVG (§10 decision 27). The site says both on one line. Generated imagery may be used only for the studio itself (episode thumbnails, lore cards, the board's silhouettes), after a board review, once the image adapter exists; the site will say so on the same line when it does.

### Kernel

The files that enforce the kernel are listed in `platform/gate/kernel-paths.txt`; no agent may change them in any lane (§10 default 14). One kind of kernel change reaches `main` without the board's merge: `upkeep_merge`, dispatcher code and no agent, merges a Dependabot patch update that changes only dependency versions in `package.json` files and `pnpm-lock.yaml` when every condition of the merge policy holds (§4 Upkeep, §10 decision 53).

Not editable by any card, vote, regime or org change, at any tier, and the site says so: the ledger; spend caps; the default 80/20 split and the 10% reserve (each supporter sets their own split at checkout; the default is not votable); the incident reserve rule; the gate; rollback; the content filter, the all-ages rating and the art policy; the broadcast delay and kill switch; and the read/write separation: no agent with write access to a build, a card or the org chart reads free text from the public. The Host, the Community agent and Biz Dev read outside text and have no write tools. The single exception is board notes: free text from the board's authenticated accounts, read by the Studio Head.

The broadcast delay and kill switch bind the stream and the host from the day they exist; nothing broadcasts today.

### The Board

The board is Kyle and whoever joins him. It acts through a private dashboard on its own site (`platform/board`, a separate free Netlify site at its own address; "/board" in these docs means that site), phone-friendly, never the command line. The public site does not link to it, and its own address answers /board with a plain not found page. Every file of the board's site is kernel, and it enforces its whole Content Security Policy (§10 decision 39). Its first screen is the Needs you inbox, usually empty, which lists the standing duties below when one is due.

The board's standing duties, the only ones the money rule and the kernel leave with it: after each payout, buying Console credit and raising Stripe's Minimum balance to the Controller's figure; refunding requests sent to hello@ within 14 days; answering any dispute before Stripe's due date; converting emergency-fund credit when an S1 card needs it; merging kernel pull requests, except a dependency patch that passes the merge policy (§10 decision 53); and adding new price-table rows to `.env`. If the board does none of them, the studio pauses or stays as it is.

Directives are forced, immediate changes: a card in stage funded with priority 0, still passing the gate, unable to breach the kernel. Directives are for a pillar being violated, a live problem, or a brand call; a Game-bucket directive is for a breach, not routine feature choice. Every directive carries a one-line public reason. Every board action is recorded with its reason.

Notes are advisory free text from a board member to the Studio Head. They are private and stored; nothing triages them yet.

Private to the board: notes, the founder's cash, hours and tokens (tracked, never published), card severity and priority, the incident list before its post-mortem, and spend caps. Public: directives and their reasons, the pool figures, money in (what supporters paid, the fees, refunds and disputes taken off it, and where the rest went, with the split supporters chose on average), whether the books were last reconciled with Stripe, Not on a card yet and any shortfall, stopped cards (paused, or didn't ship) with the reason in plain words and where their money went, the studio-billed and overhead ledger rows, each role's model on /team (§10 decision 26), each supporter's number on the cards their money reached (never a name, an email, or an amount or time per supporter; a number belongs to one receipt email, stored only as a hash), and everything the system does on its own (§10 decisions 42 and 46). Agent events are public only as fixed lines from their type, tool name and step code, never a path, a command, a message or a tool's output.

Controls on the board's site: the Needs you inbox (`board_needs_you`); pause and resume; the agent mode; Go live; file a directive, a card (with its horizon) or a note; horizon, rank, cancel and resume on each card; the spend caps, the monthly cap, the studio-wide daily limit on immediate credit and the usage tier cap (`set_caps`); recording each Console credit purchase (`record_credit_purchase`); the cooling window (`set_cooling_window`); a veto on each card, undealt and hidden agent cards included (`set_card_veto`); each role's pause (`set_role_pause`); and the job list, each job with its recent runs and Run now (`enqueue_manual_job`); the card supply line and Draft to the floor (`card_supply`, and `draft_card` queued through `enqueue_manual_job` with the shortfalls and the open cards). Needs you also lists the ceiling pauses the resume rule will not resume, the cards holding money whose approval is not current, a card supply short of its floor, and the Janitor's open findings. Board members read every card; the public reads an agent-written card only while its approval is current. Access: a Supabase Auth magic link to the board's and the moderator's emails only: sign-ups are off, the link never creates a user, and the seed creates each member's user; every state-changing board action needs the TOTP second factor, except the moderator's pause and the board heartbeat (§10 default 19). A moderator account holds pause rights only (the studio's, and a role's, which only the board resumes), and the kill switch once the stream exists.

## 5. Business model

### Rails

Stripe Payment Links: a one-off contribution link with a custom dropdown for the split, so the choice arrives in the webhook with no custom checkout. The webhook accepts eleven values, from 100/0 to 0/100 Agents/Studio in steps of 10, with 80/20 the default (`SPLIT_MAP` in `platform/supabase/functions/_shared/split.ts`). Stripe Canada's published card fee is 2.9% plus CA$0.30, 0.8% more for a card issued outside Canada and 2% more when a US-dollar payment is converted (§9); disputes go through Stripe's flow and the reserve absorbs them. Membership tiers and Twitch Bits are in §4 Not built yet, and so are sliders on the site in place of the dropdown ([Split slider on the site, in place of the checkout dropdown](BACKLOG.md#split-slider-on-the-site-in-place-of-the-checkout-dropdown)).

Contributions credit the meter immediately up to $50 of agent credit (the agents' share after the incident carve-out) per payer per New York day; the rest of that credit is held and credits after 14 days, released hourly, while the 10% reserve and the incident reserve are credited at once (`docs/specs/refunds-and-holds.md`). The payer is identified by a hash of the Stripe card fingerprint, falling back to a hash of the email, and the Privacy page says so (22 September 2026). A studio-wide daily limit on immediate credit is a second backstop: across all payers, credit above it is held the same way. It defaults to $500 and the board sets it at /board (22 September 2026).

### The split

Every contribution is divided. The chargeback reserve takes 10% off the top; it is mechanical and not adjustable. The remainder goes to Agents (the compute pool) and Studio by the supporter's chosen split, default 80/20. Of the Agents share, 5% goes to the incident reserve until it holds $500. Studio income is therefore a distribution set by supporters; Humble Bundle's experience is that most supporters leave defaults, so the default carries the economics and the choice carries the trust. A 50/50 headline is not used anywhere: Twitch's move to 70/30 was a response to years of resentment of the 50/50 split, and 50/50 says half the money builds nothing.

The studio share pays Stripe's fees on the studio's own purchases, currency conversion, HST and overhead: the startup probe's model usage and session time, which the ledger records publicly as overhead and which never touches the pool (22 September 2026).

### Refunds and disputes

A refund or a dispute reverses the contribution's split and any held credit (`docs/specs/refunds-and-holds.md`). Its credit comes off that payment's own allocations, newest first, from every card it reached and from Not on a card yet, and each place gives up only that payment's unspent money there: a card spends its oldest money first (`docs/specs/money-logic.md`). Money already spent comes off Not on a card yet, which can go below zero; that shortfall is shown and alerted, and is not repaid from new money. Stripe keeps its processing fee on a refund or dispute: the row takes off the whole amount reversed, and the fee part comes off the studio share, so no supporter's money covers it. Stripe's dispute fee is booked by the Controller once per balance transaction.

### Terms, refunds and winding down

The Terms and the Refunds page are one document with a whole-number version (`docs/specs/legal-copy.md`). `platform/site/src/lib/terms-versions.ts` holds every version's words, and a posted version's words are never edited. A version is posted by inserting its row into `terms_versions`, through its own migration, applied only after the site carrying its words is live; the row records when it took effect, and the pages show the version in force with that time and list the earlier ones. A change applies only to contributions made after it is posted: a contribution keeps the version in force when its checkout started, which `terms_version_at` gives from the Checkout Session's created time.

The refund rule is the full amount paid, on request within 14 days, even when the money was spent. Stripe keeps its fee on a refund and the studio share pays it. Where Stripe cannot refund a payment, the studio returns the money another way agreed by email. A parent's or guardian's request to refund a contribution made without their permission is honoured in full with no time limit. To contribute a person must be an adult where they live, or have a parent's or guardian's permission. Contributions are charged in US dollars, and the studio adds no tax. The studio has no cryptocurrency, coin, token or NFT; the coin drawn on the site is a symbol for money in US dollars.

If the studio stops, contributions close first and any card being built is finished or cancelled. Each contribution then gets back its own agent money that has not been spent: its credit still on hold, its share of what is left on each card bar it reached, and its share of the agents' unspent money on no card's bar, each in proportion to what it put there. The 10% reserve and the emergency fund are kept for 120 days and then refunded the same way. The studio's share is not refunded. A final ledger lists any money that could not be returned.

The Terms name the operator (Kyle Smith, an individual in Ontario) and hello@clayhouse.studio for Ontario's internet-agreement disclosure, and publish no mailing address or phone (§10 decision 55). Stripe's terms checkbox at checkout waits on the board (`BOARD-SETUP.md` step 12); nothing waits on it.

### Costs

Everything the studio runs on is free, and the only money it spends is what players put in (§10 decision 35). The standing cost is agent compute. The configured agent rate starts at $5 an hour (`AGENT_HOURLY_RATE_USD`) and the measured figure replaces it; for scale, the first three test runs and the three board directives cost $0.8242 across 65 ledger rows (`docs/specs/week1-runs.md`). Agents run only when funded, so spend is a ceiling the audience sets.

### Compute account and mode

Before the cutover the fleet runs attended: sessions run through Claude Code on the founder's subscription, sandboxed to the card's worktree, only while a board member is signed in at /board, and are billed to the founder, never to the pool. After the cutover card sessions run unattended as Claude Managed Agents sessions on the studio's own Anthropic organization, a separate pay-as-you-go organization with prepaid Console credit, auto-reload off and a $500 monthly limit raised by hand as the meter grows (§10 decision 25). Console credit is bought only with contributions Stripe has paid out, never with the founder's money (§10 decision 23), and the throttle never lets unattended sessions spend more than the credit bought and recorded. The founder's subscription is never used unattended.

### Possible later income

Ideas the board has not taken up, recorded so they are not lost: the card and gate pipeline as a service for Early Access studios; sponsors on credits-for-logo terms; a paid supporter pack on Steam once the Steam release path exists.

### Canada admin

Viewer payments to a for-profit are business income and consideration for a supply; GST/HST (13% Ontario) applies past the $30k small-supplier threshold. Copy says "contributions," never "donations." The board reviews HST registration when cumulative contributions reach $15k, and registers before tiers with named benefits ship, since those are sales (`BOARD-SETUP.md`). The platform repository stays private; the games get a license only with the public seed-1 mirror, and nothing public says open source before then.

## 6. Architecture

### Build 1

Build 1 is what the studio runs on at Go live, and `docs/ROADMAP.md` is its checklist: the public site (landing, contribute, ledger, how it works, team, roadmap and the legal pages), the board's own site, the Stripe webhook and the money logic in Postgres, the dispatcher, the gate, the role specs and Dust. The site shows what is building, the cards open for funding (filtered by the game and the studio, and the next game once it has cards), what shipped and the ledger (`docs/specs/site-layout.md`). Contributions made before Go live are credited like any other. Each contributor gets one supporter number at their first payment, in order from 1, and it is a founding number when that payment came before Go live; no queue position is promised (`docs/specs/money-logic.md`).

### The public site's data

The public site holds no Supabase client and opens no Realtime connection. Every figure on it comes from two documents on its own origin, which one Netlify Function builds with the publishable key and the CDN caches: `/api/live` (the figures that move: the pool, the studio's pause, the books, the stopped cards, each listed card's state (its stage, horizon, ship time, bar and funding), the newest events and deploys), cached 60 seconds, and `/api/cards` (the card text, the roles and the posted Terms versions), cached 300 seconds. A visible tab reads `/api/live` once a minute and a hidden one reads nothing, so Supabase egress is bounded by the number of document builds, not by the number of readers, and figures run up to about three minutes behind the database. A card's own page reads `/api/card/:id` from the same function family, cached 60 seconds like `/api/live`, and `/thanks` posts the Checkout Session id to `/api/thanks`, which is never cached (`docs/specs/supporter-pages.md`, decision 48). `/reports` reads `/api/reports`, the published weekly reports, cached an hour (`docs/specs/studio-reports.md`, decision 50). The board site signs in and reads Supabase directly (`docs/specs/site-snapshot.md`, decision 47).

### The pipeline

A Node dispatcher runs on a one-minute tick and ticks only while it holds the dispatcher lease, so two dispatchers never run cards at once. Each tick first deals the approved agent cards whose cooling window has passed and resumes the ceiling-paused cards the rule may resume. It reads Supabase (`dispatcher_cards`) for the highest-priority runnable card: stage funded, horizon now, approved when an agent wrote it, vetoed by neither the Director nor the board, with an executor role that is not paused, within the throttle. In attended mode it runs Claude Code in a git worktree outside the repository. In unattended mode it creates a Claude Managed Agents session with the repository mounted read-only at the card's base sha; the agent hands back its work as a patch file through the `submit_patch` tool, and the dispatcher applies it in its own worktree. Either way the dispatcher checks that the change stays inside the card's lane and off every kernel path, checks the card's `check:` lines, commits, pushes `card/<id>-<lane>` and opens a pull request. GitHub Actions runs the gate. On a green `gate` check at the pull request's exact head sha, the dispatcher re-reads the pause and the card, and squash-merges with that sha only while `main` still points at the card's base; if `main` moved, the card goes back to be gated again. Netlify deploys. The production smoke test runs no card code: it checks the served build sha, the served config checks, that each served `/config/*.json` matches the merge commit byte for byte, and that the gate is green at the merge sha (§10 decision 34). On a pass the card goes live; on a failure the previous deploy is restored from `last_green`, a revert commit lands on `main`, and the card is rejected with the failing check. A failed revert pauses the studio and alerts the board. `main` has no branch protection, which the private repository's plan does not offer; the exact-sha merge is the protection. No agent-written code runs on the dispatcher's host: the role jobs' sessions there hold Read, Glob and Grep only, never Bash, and are denied the code clone's `.env`, the host's env folder and every `.env` file under the home folder.

Role work runs through a job queue instead of a scheduler inside the dispatcher: `jobs` names each job, its role, whether it calls a model and whether it runs while the studio is paused, and `job_runs` holds each run with its origin (board, schedule, event or operator). pg_cron and the board queue runs; a key makes each enqueue happen once, and a job holds at most one queued scheduled run. After the card path, every tick starts the oldest queued run that can start, one job at a time, and finishes one that cannot as skipped with its reason. A model-calling run starts only when the board queued it and a board member is signed in at /board, in either studio mode, billed to the founder; no role job spends studio or supporter money until an operations budget exists. `docs/SYSTEM.md` is the map.

After the heartbeat, a tick that holds the lease runs the outbound lane: the ship posts for public cards live within the last 6 hours and the post for the newest weekly report, each claimed in `outbound_posts` before it is sent, at most five a tick, with a 10-second timeout, inside its own try and catch, so Discord can never delay a card or the heartbeat. The webhook addresses live only in the dispatcher host's `.env` (`docs/specs/studio-reports.md`).

### Budget throttle

Every agent turn writes usage at list price to `ledger`. Available money is the pool balance minus the studio reserve (zero at launch) minus what other cards hold: a card waiting, open or paused holds its funded money not yet spent, and a building card holds what is left of its session budget. A card starts only if available covers its ceiling. Turn cap 60 per session. Concurrency is one session when available covers the smallest runnable ceiling, and two when the balance is at least twice the hourly rate. The daily cap is measured against the day's starting balance. In unattended mode a session's budget is also bounded by the Console credit left, the monthly cap, the monthly cap of the Anthropic usage tier when the board has reported it, and what remains of the daily cap, and a credit, spend-limit or usage-tier error pauses the studio with an alert instead of failing the card. Caps live in `studio_state` and are edited from /board; the environment values are the initial seeds. Zero balance: the agents idle.

### Runtime and layout

Game runtime: Phaser 3 with TypeScript and Vite. Static build to Netlify; `Phaser.HEADLESS` in Node for playtest bots. Each seed keeps a deterministic, seeded simulation core (`seed-1/sim/`) separate from rendering so bots run at 1000× realtime.

Execution: the executor and target folder are columns on the card. Game and QA cards run on Builder A or Builder B, QA reproductions on QA, studio cards on the Platform Builder. One repository with two top-level folders: `platform/` (the public site, the board's own site in `platform/board`, the dispatcher, the gate package, Supabase, the role specs and ops) and `seed-1/` (the game, `config/`, `content/`, `sim/`, CLAUDE.md). `seed-1/` never imports from `platform/`, so a seed can be lifted into its own repository. The dispatcher runs attended on the founder's Mac before the cutover. After it, it runs unattended on GitHub Actions in this public repository, from a read-only checkout of main, one run of up to about six hours after another (§10 decision 61, `docs/specs/actions-host.md`); the daily jobs run on Actions in the board's private ops repository. The board's Mac host (§10 decision 38, `docs/specs/mac-host.md`) is retired. An always-on paid host, reusing the Ubuntu provisioning in `platform/ops`, waits until player money pays the overhead ([Move the dispatcher off the Mac](BACKLOG.md#move-the-dispatcher-off-the-mac)).

Role models resolve from environment tokens (`MODEL_DIRECTOR`, `MODEL_BUILDER`, `MODEL_HOST`) when a session starts, so a model change takes effect without a re-seed (22 September 2026).

### Technical risks

Runaway spend: the per-card ceiling, the ledger, the daily cap, the monthly cap, the Console credit bound and the Console limit. Agents breaking the thing running them: the kernel paths no card can change, the board's sign-in on its own site built only from kernel files, and the studio code lane closed until the board opens it. A payment address other than the Payment Link: the gate's payment-host scan over the built site. Silent failure: healthchecks.io and ntfy alerts, and the pause on a failed revert. A dispatcher run ending or GitHub Actions failing to start the next one: each run drains and starts the next, a 30-minute schedule restarts it, and the healthchecks.io alert covers the rest (`docs/specs/actions-host.md`). Running out of free Actions minutes in the private ops repository, which stops the daily jobs (`docs/ROADMAP.md` standing facts). Agents shipping systems rather than fun: the idle genre and the bot's progression invariants in the gate.

## 8. Risks and kill conditions

Three failure modes matter most. Novelty decay before the funding loop closes (the Nothing, Forever and Claude Plays Pokémon curves), answered by a regular appointment supporters can count on: cards going live, the weekly report on /reports and the ship posts on Discord. A host saying something bannable (Nothing, Forever's 14-day suspension), answered by the filter, delay and kill switch in the kernel before any host runs. The board becoming the on-call engineer, answered by the alerts, automatic rollback, the incident reserve and the board-time limits below.

Abuse and mitigations. Prompt injection: the read/write separation in the kernel. Cost drain: per-card ceilings, the daily cap, the monthly cap and the Console credit bound. Chargebacks: the $50 daily credit limit per payer keyed on the card fingerprint, the 14-day hold above it, the studio-wide daily credit limit and the 10% reserve. Brigading, once free voting exists: voter identity with a minimum account age, one vote per account, quorums, the gate. Harassment through names and credits, once the name pipeline exists: the deny-list, the cooling period, board approval.

Kill conditions, counted from Go live (the board's criteria; the two viewer-count lines were removed on 22 September 2026):

| After Go live | Kill if | Pivot instead |
|---|---|---|
| 7 days | under 25 unique funders, under $500 funded, or board time over 25 hours | drop 24/7; run a weekly two-hour live show |
| 30 days | under 100 funders, under $2,000 cumulative, or board time over 12 hours a week | drop the meter; run as a public demo |
| 90 days | under $6,000 cumulative, or board time over 10 hours a week | archive; publish the post-mortem; open-source the vote and meter kit |

The pivots were written for a streamed studio; restating them for the site-first studio is an open board decision (`BOARD-SETUP.md`).

Dispatcher loop (every 60 seconds, while holding the lease). Deal the due agent cards (`deal_due_cards`) and resume the ceiling-paused cards the rule may resume (`resume_due_by_rule`), both nothing while the studio is paused. Read `studio_state`; if paused, sleep; if `agent_mode` is attended and no board session is active, sleep. Read the pool and the caps; compute what is available (§6 Budget throttle). Select the runnable card with the lowest priority number, then the oldest, whose ceiling fits (an S1 card may also draw the incident reserve). Set `building`; run the session (§6 The pipeline); write every turn to `ledger` and `agent_events`; stop at the ceiling or the turn cap, then `paused`. On completion push the branch, open a pull request, set `gated`, wait for the gate, merge, deploy, smoke, and set `live` or `rejected`, restoring `last_green` and reverting on main after a failed deploy or smoke (§10 default 14). Attended sessions skip the pool and daily-cap checks and are billed to the founder (§10 default 7). Then, however the card path ended, start the oldest queued job run that can start (§6 The pipeline). After the heartbeat, run the outbound lane: the Discord ship and weekly posts, inert with no webhook set (§6 The pipeline).

Stripe webhook (Supabase Edge Function). It handles `checkout.session.completed` (read the amount and the `split` custom field; compute the reserve, agents, studio and incident amounts; insert `contributions`, stamped with the Terms version from the session's created time; credit the pool and the incident reserve; place the credit through the waterfall; hold credit above the daily limits); `charge.updated`, which credits a paid session whose Stripe fee arrived after the session event, keyed by the Checkout session so a payment credits once (`docs/specs/stripe-late-fee.md`); and `charge.refunded`, `charge.dispute.created` and `charge.dispute.funds_withdrawn`, which reverse a contribution. It is idempotent on `stripe_event_id`. Held credit is released hourly by pg_cron (`docs/specs/refunds-and-holds.md`), and `waterfall_sweep()` runs every five minutes (`docs/specs/money-logic.md`).

Gate (GitHub Actions workflow `gate`, `platform/gate/ship-gate.sh`). The kernel checks run before any card code; then, in order, stopping at the first failure:
- Every lane: secret scan; banned phrases (the deny-list scan over the folder, the changed files, the root docs, path names and the commit message); runtime-token deny (NaN, undefined, stray task markers, stand-in text and the rest of the list).
- seed-1, config lane: the headless bot, then the build.
- seed-1, code lane: typecheck, tests, the headless bot, then the build.
- platform: typecheck and tests of the dispatcher, supabase and site packages; the Deno function tests when the change can reach `platform/supabase/`.
- end-to-end, beside the platform job on its own runner, when the change can reach the site: the site build and the Playwright end-to-end suites of the site and the board site (`docs/specs/gate-e2e-job.md`).
- Last, after every build: runtime-token deny over the HTML the build just wrote.
- Frames, when detect reports `render=true` (a non-test file under `platform/site/src/`, or anything under `platform/site/public/`, `platform/site/e2e/`, `seed-1/render/` or `seed-1/e2e/`, or `platform/site/index.html`, `seed-1/index.html` or `seed-1/content/strings.json`): the `frames` job, on a fresh runner that runs no card tests and no card code in Node (the screenshot specs, their configs and every file they import are kernel), restores the kernel from the base on a card branch, installs without lifecycle scripts and runs the kernel screenshot specs on the change and on a worktree of the base: every route in `platform/site/e2e/routes.ts` at 375, 768 and 1440 (`route-shots.spec.ts`, failing on any request off the preview and on a data route that did not draw the fixture), and the game's canvas at four fixed states and its page at 375 (`seed-1/e2e/frames.spec.ts`, reading the states `e2e/frame-states.ts` makes from the base's sim before the change is drawn). `frames-diff.sh` keeps each frame that differs byte for byte from the base's as a before and after pair with `changed.txt`, uploaded as the `design-frames` artifact for one day; the gate job requires the frames job when render is true.

The detect job selects the work by changed path (`platform/gate/changed-paths.sh`), and runs the scans above over each folder it selects. The seed-1 jobs run for a change under `seed-1/`; the platform job for one under `platform/` or `docs/`; the Deno tests for one under `platform/supabase/`; and the site builds, their scan and the end-to-end suites for one under `platform/site/`, `platform/board/` or `platform/agents/`. A change only under `docs/`, `platform/dispatcher/`, `platform/ops/` or `platform/supabase/` builds nothing. A path under `platform/` that no narrower rule names selects all the platform work, and a path outside `seed-1/`, `platform/` and `docs/` selects everything. The `gate` job fails closed: it fails when detect failed, when a flag is missing or not exactly true or false, and when a job detect selected did not pass.

The headless bot runs `seed-1/sim` on a fixed seed for 10 simulated hours and asserts the invariants: dust never negative, every number finite, at least one unlock per simulated hour, and the same seed giving the same state hash. On a `card/*` branch the workflow restores `platform/gate` from the base commit and runs the kernel guard before anything else; it fails a change to a kernel path or to a board-only design file in `platform/gate/design-paths.txt` (`rule=design-path`), and the dispatcher refuses both before any gate run.
